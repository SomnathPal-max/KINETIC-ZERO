2. Product definition
One-liner
Show it once. It automates forever, and refuses to act on anything it cannot prove.

Problem
Indian MSMEs, hospitals and CA firms do much of their back-office work in web portals without APIs: vendor payouts, GST
data entry, insurance claim forms. Classic RPA breaks when a portal changes one button or ID and needs engineers.
Prompt-based agents need prompt skills and can confidently click the wrong thing or act on a misread invoice.

What we build (the demo-able loop)
-     Verify: upload a vendor invoice (PDF text layer; image is P1). Gemini extracts fields with evidence quotes. The Guard
      checks them with deterministic gates, evidence grounding and policy citations, then returns PROCEED, ESCALATE or
      BLOCK. The Guard can overrule the AI's own proposal.
-     Teach: an operator performs the claim once in the portal inside a Playwright browser. The recorder compiles the actions
      into a workflow JSON with variables bound to invoice fields.
-     Run: the runner replays the workflow on a new invoice. Before any browser action, the Guard must return PROCEED
      (or a human approves an ESCALATE).
-     Heal: a judge clicks Mutate. A naive replay breaks. KINETIC-ZERO repairs through four tiers, verifies the patch, asks a
      human before irreversible actions when confidence is low, and stores the patch.
-     Prove: a Results tab shows benchmark tables from real runs: heal success, wrong-action rate, LLM calls per run,
      latency, Guard catch rate, false-block rate.

Soft components and score
    S = fraction of fields whose evidence is found in source_text (rapidfuzz partial_ratio >= 95)
        AND whose value appears inside that evidence
    A = pass1/pass2 agreement fraction after normalisation        (passes == 2)
        1.0 for pdf_text, 0.5 for image with one pass             (passes == 1)
    P = fraction of policy claims whose retrieved top-3 clauses contain the claimed rule number/keywords

    data_trust_score = round(100 * (0.45*S + 0.35*A + 0.20*P))                              # heuristic weights, label them as such

    verdict = BLOCK     if any hard gate has status FAIL
              ESCALATE elif any gate has status ESCALATE or data_trust_score < 70 or any UNSUPPORTED claim
              PROCEED   else
    ai_overruled = (proposal.decision == "APPROVE" and verdict != "PROCEED")

- Every check emits a claim (atomic statement + evidence + status + clause_id). The explanation is built from a template
  over failed claims, never by an LLM.
- Be honest in UI copy: weights are hand-set heuristics; safety comes from the hard gates, not the score.
- A valid GSTIN checksum proves format only. G4 uses the mock registry for status. Say so in the UI.


6.3 Policy index (Agent B)
- Source: data/policy/vendor_payment_sop.md (Appendix D, fictional company SOP). Parse by ### VP-x.y Title
  headers into chunks {clause_id, title, text, numbers[], keywords[]}.
- Index: embed each chunk with the Gemini embedding model; store vectors in data/policy/index.npz (cached). Lexical
  score from own TF-IDF/BM25-lite. Retrieval score = 0.6 cosine + 0.4 lexical. If embeddings are unavailable, fall back to
  lexical only and log a warning.
- API: policy.retrieve(query, k=3) -> list[Clause] with scores. policy.exists(clause_id) and
  policy.numbers_in(clause_id) for G8.
- data/policy/policy.json holds the machine-readable twin of the SOP thresholds (Appendix D). CI test: every number
  in policy.json must appear in its clause text. This keeps rules and cited text from drifting apart.


6.4 Extractor (Agent B)
- PDF input: pypdf text layer is source_text (ground truth for grounding). Ask Gemini for fields, line_items and a
  verbatim evidence snippet per field, using JSON schema output at temperature 0.
- Image input (P1): ask Gemini for a transcription into source_text and run two independent passes (different prompts)
  to fill pass2_value. Any disagreement or failed G1/G2 on an image routes the field to the human escalation card.
- Then ask Gemini for the AgentProposal from the extraction and the retrieved clauses (prompt in Appendix B). Guard
  verifies and may overrule it.


6.5 Recorder and compiler (Agent C)
-    POST /api/teach/start launches headed Chromium with context.add_init_script(recorder.js) and
     expose_binding('k0_event', ...). The recorder listens in the capture phase for click, change and blur of text inputs. It
  ignores data-k0* attributes and noise (focus clicks followed by a fill).
- For each event the backend computes the Fingerprint, builds locator candidates in priority testid > id > name >
  role+name > css, saves a screenshot, attaches the latest narration, and pushes the step to the Console over SSE.
- Variable binding: if a typed value equals a field of the loaded invoice after normalisation, set value_from to that field.
  Otherwise store literal.
- POST /api/teach/stop compiles: merge keystrokes, drop noise, set irreversible=true on the last click when its text
  matches submit|pay|confirm|send|approve (operator can toggle), derive negative_terms (cancel, delete, reject,
  back, clear), derive expect from the settled page (field value, next URL, or next heading), generate intent strings with
  one batched cached LLM call, validate with pydantic, save data/workflows/<id>.json.
- Workflow JSON must never contain data-k0 strings (test it).

Run loop
- Gate: call guard.verify. BLOCK: stop, outcome BLOCKED, zero browser actions. ESCALATE: show a human card
  and continue only on approval. PROCEED: continue.
- For each step resolve the target through the tiers below, run the Patch Verifier, perform the action, check expect within
  3 s.
- After the last step read GET /portal/api/state and set outcome by comparing the portal's recorded state to the
  expected claim (outcome-based oracle, not selector-based).

Tiers
    Tier    Name                       Logic

    0       Exact                      Try the recorded locator, then alt_locators. Accept only if exactly one visible match and
                                       similarity(recorded_fp, live_fp) >= 0.55. The similarity guard stops a reused ID that now
                                       points at something different.

    3       Memory                     Look up a stored patch for (workflow, step, page signature) in SQLite. If found, apply it through the
                                       Verifier. 0 LLM calls.

    1       Fingerprint scoring        Enumerate visible, action-compatible elements. Score each (formula below). Accept if top >= 0.62 and
                                       top - second >= 0.12. Exclude candidates whose text hits negative_terms unless the recorded
                                       fingerprint also does.

    2       LLM selection              Send intent, action, recorded fingerprint and the top-8 candidates as compact JSON (index, tag, text,
                                       label, role, type, attribute subset, bbox centre), optional screenshot. Output {choice: index|null,
                                       confidence: 0-1, reason} at temperature 0. choice null or confidence < 0.7 means fail safe:
                                       pause for the human.

Order of attempts: Tier 0, Tier 3, Tier 1, Tier 2. Modes: baseline = Tier 0 using only the recorded locator with no similarity
guard (the naive replay a judge compares against). k0_tier1 = Tiers 0, 3, 1. k0_full = all tiers.
    tier1_score = 0.30*text_sim + 0.20*label_sim + 0.10*role_tag_match + 0.10*type_match
                + 0.10*attr_overlap + 0.10*dom_path_sim + 0.10*pos_proximity
    text_sim   = max token_set_ratio(candidate text/aria/value/placeholder, recorded text) / 100
    label_sim = token_set_ratio(candidate label/nearby text, recorded label/nearby text) / 100
    attr_overlap = Jaccard over tokens of id, name, classes, placeholder
    pos_proximity = 1 - min(1, euclidean(bbox centres) / 0.5)


Patch Verifier
- Element is visible, enabled, tag/role compatible with the action (fill needs input/textarea/select).
- Element text does not match any negative_terms unless intended.
- After acting, expect holds within 3 s. For fills, read the value back. If it fails, try the next-best candidate once (only for
  non-irreversible steps); otherwise stop and escalate.
- Human gate: if irreversible and (tier 2, or tier 1 with margin < 0.20) then pause and show the live screenshot with the
  target highlighted, the reason, and Approve / Reject. In benchmarks nothing auto-approves; such runs count as
  ESCALATED.
- On a verified heal write the new locator and fingerprint to the workflow (version + 1), store a HealEvent and a memory
  patch, and emit an SSE event with an old-vs-new DOM diff.

Appendix A. GSTIN checksum (verified reference)
A GSTIN has 15 characters: 2-digit state code, 10-character PAN, entity code, the letter Z, and a check character
computed with Luhn mod-36 over the first 14 characters. Public sources note that GSTN does not publish the formula, so
treat this as the widely used method. Verified test vector: 27AAPFU0939F1ZV is valid (check char V). Changing the last
character must fail. Other sample numbers found in blogs did not pass; generate every fixture GSTIN with
gstin_checksum, never type one by hand.

 CH = "0123456789ABCDEFGHIJKLMNOPQRSTUVWXYZ"

 def gstin_checksum(first14: str) -> str:
     total = 0
     for i, c in enumerate(first14.upper()):
         v = CH.index(c)
         prod = v * (1 if i % 2 == 0 else 2)
         total += prod // 36 + prod % 36
     return CH[(36 - total % 36) % 36]

 def gstin_ok(g: str) -> bool:
     g = g.strip().upper()
     return len(g) == 15 and g[13] == "Z" and gstin_checksum(g[:14]) == g[14]

 assert gstin_ok("27AAPFU0939F1ZV") and not gstin_ok("27AAPFU0939F1ZX")
